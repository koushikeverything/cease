2What happened so far

🗂 Idea → a written product spec

You already had CEASE-plugin-spec.md: a full product specification for finding counterfeits inside a brand’s own systems — the support inbox, the payment disputes, the catalog, the ad account — instead of crawling the open web the way every incumbent does.

Why it mattered: it gave this stage something concrete to test rather than a vague wish, so the work went straight to “does this need building at all?” rather than “what is it?”

🗂 Defined → requirements, evidence, and a verdict

The system searched everything that already exists — your connected apps, the connector directory, your installed skills, your plugin catalog, and the features Claude ships natively — then made one real call against each capability rather than trusting a catalogue description. Fifteen capabilities were tested.

Why it mattered: two things the product spec assumed turned out not to be true, and both were caught before a line of code was written rather than halfway through building:

  • Support-inbox search is not smart. The spec assumed Claude could search the support inbox by meaning. It can’t — Gmail search only matches keywords. A test search for counterfeit language returned 201 results whose top hits were all newsletters that happened to use the word “fake”. The highest-precision channel in the whole product would have been its noisiest. The fix is now a requirement: retrieve broadly, then have the model read and classify before anything reaches you.
  • The web tool can search but not save. Firecrawl, your connected web-search tool, has no page-capture ability in this setup — so evidence archiving was rerouted to the browser before the design depended on the wrong tool.

Produced: SPEC.md — 39 requirements, 20 acceptance expectations, 10 failure behaviours, explicit exclusions, and the exact permissions the plugin may ask for. Plus docs/leverage/2026-09-17-manifest.md — the evidence record behind the verdict.

🗂 Designed → the plugin’s actual shape, drawn before any code

Every one of the 39 requirements now maps to a specific piece of the plugin, and each mapping cites the platform fact that makes it legal — so when a platform fact later changes, the affected designs can be found mechanically instead of rediscovered.

The shape: 8 skills (baseline · sweep · check · evidence · enforce · testbuy · pursue · brief), 5 investigator agents, one blocking hook, 9 legal templates, and no scheduler — because Claude already has one.

Three things the original product spec got wrong, caught by reading the current platform rules rather than trusting the document:

  • It planned a commands/ folder. That’s legacy now — so the six commands and seven skills collapsed into one set of eight skills. Less surface, same capability.
  • Commands are typed /cease:check, not /cease check.
  • It put legal templates in a top-level folder; they now sit with the skill that uses them, so they cost nothing until that skill actually runs.

The signature gate got designed properly — it’s the reason this is a plugin at all. The platform’s hook rules were listed as unverified in the system’s own knowledge, so they were fetched from the live documentation rather than recalled. Three findings changed the design:

  • It must not block your ordinary email. The gate only intervenes on messages carrying a case marker, or on text that reads like a legal instrument in two or more places. Everything else passes untouched.
  • It checks that what’s sent is what you signed — by fingerprinting the text, so approving draft A can’t send draft B.
  • It fails closed. Missing or unreadable signature record means blocked, never “assume it’s fine”. And there is no timeout that quietly files for you.

Produced: docs/design/2026-09-17-cease-plugin-surface.md — every description written out word for word, the triggering tests that will prove they fire correctly, the security table naming which file enforces which promise, and an 18-step build order.

🔨 Built → the plugin exists, in 15 commits

All 19 planned pieces are written, tested and committed on a working branch: 8 skills, 5 investigator agents, the signature gate, 9 legal templates, 36 triggering tests and 120 automated tests — all passing.

The build ran one piece at a time, each committed separately, so it can be reviewed or reverted in parts rather than as one lump.

Four real bugs were caught by running the code rather than reading it — which is the point of building in small validated steps:

  • The evidence system would have declared every case tampered with. A path-handling mistake meant that when a case was checked, every screenshot and saved page came back "missing since capture". Chain of custody — the thing the case file exists for — would have been broken for every real case, while the test suite looked green.
  • The investigator agents would have worked here and nowhere else. They named a connector using an identifier unique to this account. On anyone else's machine they would have silently had no search ability at all. This is now blocked by an automatic check, because it was the second time the same mistake appeared.
  • The safety check for overclaiming was itself broken — it flagged the very sentence forbidding the overclaim. Fixed, then deliberately fed a real overclaim to confirm it now catches one.
  • A crash waiting in the signature gate's fallback path — the branch that runs precisely when things are already going wrong.

One design flaw was found and fixed mid-build. The plan said that if the gate cannot read an outgoing message it should block everything. That turned out to be incoherent — and would have blocked your ordinary email. It now keys off whether CEASE itself has an unsigned document waiting: if it does, it blocks; if not, your mail goes through untouched.

✅ Checked → three independent reviewers, and the main promise didn’t hold

Three reviewers examined the plugin separately, none of them told how or why it was built. The official validation tools ran for the first time and passed on all four targets. Then the reviewers found what the tools can’t.

The serious one: CEASE could approve its own legal notices. The promise is that nothing goes out unless a real person approves it. The approval was a file on disk — and the part of CEASE that writes the notice could write that file too. No villain required: you say “just file it”, it takes the shortcut, and a document sworn under penalty of perjury goes out with your name on it, unread.

Now fixed, the way you chose. Before sending, CEASE looks back at the conversation for a message you typed approving that specific document. It can write any file and run any command; it cannot type a message as you. The document also has a short code, so approving one version can’t send a different one. Every way of faking it is tested and fails — including CEASE saying the magic words itself, and vague replies like “yes” or “go ahead”.

Four more real defects, all fixed:

  • The plugin would have bricked itself on a real install. A setting the signing step needed isn’t available where that step runs — so nothing could ever be signed, while the guard kept blocking everything. Permanently stuck, and the reference manual said so plainly; the build read it and shipped past it anyway.
  • The guard watched the wrong door. Most takedown reports are web forms — Amazon, Meta, TikTok — not emails. Only email was guarded. Now forms and commands are too.
  • It would have blocked your own emails to your lawyer. It reacted to words like “DMCA”, which you use constantly. Now it only reacts to the sworn legal language that appears inside an actual notice, and ignores quoted replies.
  • Your real distributors would have shown up as suspects. The rule that protects them was tested in isolation, passed, and wasn’t actually applied where it mattered — the single loudest complaint about tools like this.

✅ Review complete → it reaches for the right tool

With the login working, the 36 triggering tests finally ran. The result that matters:

  • Asked for the right thing, it picks the right tool: 14 out of 16. And zero cases where it picked the wrong one — the risk we were most worried about, eight similar skills confusing each other, simply didn’t happen.
  • Asked for something else, it stays out of the way: 16 out of 16. No barging into work it doesn’t own.
  • Two cases where it answered correctly without formally invoking the skill. At one run each that’s noise, not a fault.

The scoreboard said 27/36 and the scoreboard was wrong. The test environment has no file access, so skills that routed perfectly then couldn’t do their work — and the automatic grader marked that as failure. One example, scored zero: “I can’t produce this week’s scorecard — the underlying data is unreachable, and I won’t fill it in with plausible-looking numbers.” That is exactly the behaviour we built. So a proper measuring tool was written that checks which skill was actually reached for, rather than judging the output.

An earlier run scoring 23/36 was thrown away entirely — that one measured a sandbox that had blocked skills from running at all. Both runs are saved so the claim can be checked rather than taken on trust.

3The leverage picture

',

The most valuable answer this stage can give is “you don’t need to build that.” Here, a lot of it came back that way.

hybrid  Build the judgement, borrow everything else

Borrowed — no code will be written for any of this: every single data source (your store, mail, payments, notes, calendar, chat, web search, browser) is already reachable through connectors, and all six scheduled sweeps in the product spec are covered by a scheduling feature Claude already has. Building a second bridge to a service that already has one is a defect, not a feature.

Built — because nothing on earth currently does it: the judgement layer. Deciding which of six legal categories a hit belongs to, scoring how much it’s costing you, never flagging your own distributors, assembling evidence that would survive a lawyer reading it, drafting the right legal instrument per platform, and refusing to send any of it without your signature.

Searches for an existing brand-protection plugin or skill returned nothing. The connectors give you access; none of them give you judgement.

Connect Shopify, Stripe and Slack decided 18 Sep

What this means
Granting CEASE read access to your store catalog and orders, your payment disputes, and posting rights to a Slack channel — through Claude’s own connector settings, not through anything this plugin stores.
Why now
You chose to build the full specification, and three of its detection channels have no data without these. Doing it before design means the design can be tested against the real tools instead of assumed ones.
Impact
Shopify is load-bearing — two requirements are unbuildable without it. Stripe costs one detection channel. Slack costs nothing; email substitutes.
Decided
None can be connected right now. Shopify and Stripe run on synthetic test data behind a swap point; Slack is replaced by email, which is real. This reverses the earlier intake answer, and the record was corrected rather than quietly changed.
Reversibility
Fully reversible — disconnect any time in settings. Nothing is copied out of these services; the plugin stores no credentials at all.
What happens next
Build adds one extra step up front — a swap point between “test data” and “real connector” — so connecting these later is a settings change, not a rewrite. A written acceptance rule enforces it: swapping in a real connector must not require editing a single skill.

5What the system learned

🧠 The rules for the most important control were verified, not remembered

The system’s knowledge pack openly marked the hook rules as unverified — and hooks are exactly what makes CEASE refuse to file anything unsigned. Rather than design from memory, it fetched the current official documentation and found details that memory would have got wrong: the precise way a hook blocks an action, and that connector tools are named with an identifier unique to each user’s account — so a gate written the obvious way would have worked on your machine and silently failed on everyone else’s.

🧠 A wrong entry was caught and pulled from the record

Yesterday’s environment check reported the Claude command-line tool as installed and its evaluation feature as unlocked. Neither could be reproduced today. Both readings have been struck from the evidence record rather than left to be trusted later — and specifically flagged as not to be folded into the system’s permanent knowledge. A living cache is only worth having if wrong entries come back out of it.

🧠 A promise the product couldn’t keep got cut before it shipped

The sweep was going to advertise ad-spend anomaly detection — spotting when your cost-per-click spikes because a copycat is bidding on your name. Checking the wiring showed no connected source for that data at all, and the two providers the original spec named were dropped earlier. The feature would have been a description that promised something the plugin couldn’t do.

It was narrowed to what actually works — finding your own creative running under another advertiser in the public ad libraries — and the overclaim was removed from the description, the requirement, the test prompts and the trigger list in the same pass. Cheap now; an eval failure and a rewrite later.

🧠 Two mistakes became permanent guards, not lessons

A note in a document is forgotten; a check that fails the build is not. Two of the bugs above are now automatic checks that will catch the same mistake in any future work: one blocks account-specific identifiers from being written into the plugin, the other blocks any claim about accuracy that hasn't been measured. A third guard ensures nobody quietly rebuilds the scheduling that Claude already provides — the easiest way to lose the work this project saved by not building it.

🧠 The same mistake, three times — now a standing rule

Three separate defects shared one shape: a rule was tested on its own, passed, and wasn’t actually connected where it counted. The evidence check, the distributor protection, and the tamper alarm all looked fine in testing while doing nothing in practice. A passing test on disconnected code is worse than no test, because it buys confidence.

There is now an automatic check that every safety rule is genuinely reachable from the place it’s meant to protect, and that every verification command is actually run by something. That one is worth carrying to every future project.

🧠 Twice now, the score measured the test rig instead of the product

Two full test runs produced numbers that said nothing about CEASE — once because the environment blocked skills outright, once because it graded a correct decision as a failure. Both looked like real results. The lesson worth keeping: before believing any score, check whether the environment could have produced a pass at all.
